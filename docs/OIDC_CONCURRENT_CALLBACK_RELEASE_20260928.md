# Concurrent OIDC callbacks: evidence and release

## Observed failure and limits

After the shared-session release, a real login passed email-code verification and loaded a present identity session at consent. The same diagnostic journey then produced three overlapping native callbacks: one succeeded and two returned an OAuth `invalid_grant` error. Three separate edge request IDs and single origin upstream timings exclude a retry inside the origin Nginx for these requests. The authorization code and state were redacted in existing logs, so their byte equality is not retrospective evidence. Browser or edge duplication remains an inference, not an established implementation detail.

A real-handler regression reproduces the same success/error pattern with three identical validated callbacks and a single-use exchange boundary. Before the fix, all three attempt the exchange, two fail, and one succeeds. Production SDK/React authorization fixtures separately issue exactly one callback per document in both auto-approved and consent-required paths.

Real-provider staging acceptance of the first correction exposed a timing gap: three client-side concurrent callbacks with the same validated digest reached the backend at different times. The first completed successfully; the other two began about 94 milliseconds later and failed. This proves identical late delivery in that controlled test, not the original phone's unobserved mechanism. Pure in-flight sharing is insufficient and that candidate was not promoted to production.

## Minimal correction

Use the existing singleflight dependency after every original state and browser-binding check. The key covers signed state, the verified PKCE verifier and authorization code. One bounded exchange supplies the unchanged native response to its waiting callers; an abandoned caller does not cancel the other callers. Retain only the final encoded successful response for ten seconds so identical late arrivals receive exactly the same native session, without another provider exchange, new session or extended token lifetime. Lookup and insertion occur within the same singleflight operation. Never retain failures. The process-local store has a hard limit of 128 entries and 64 KiB per entry, evicts the earliest expiry at capacity, and removes payload references on a timer even without later traffic. Oversized responses still complete normally but are not retained. Missing/incorrect binding and expired state still fail before lookup; after the short window, replay again fails closed. HTTP responses remain `no-store`.

A bounded SHA-256 callback digest is logged only after validation. It is anonymous correlation, never authorization; raw code, state, verifier and tokens remain excluded. This supports a future real-phone check of whether the overlapping callbacks are identical. Current deployment has one application instance; this change does not provide cross-instance deduplication.

## Validation and release

- The original handler failed the three-request regression with two errors and three exchanges. The correction passed the concurrency, binding/key isolation, leader cancellation and completed replay checks, including race detection. Handler, service and middleware suites passed; source/provenance checks and strict change-spec validation passed.
- Real staging reproduction against the previous immutable release passed ordinary password → provider authorization → native callback → `/auth/me`. Repeating one new callback concurrently with its original binding produced one successful native session and two login failures. The successful session belonged to the expected dedicated synthetic account. This used the actual identity provider and backend, with no callback stub.
- Consolidated adversarial review found no current implementation blocker; independent focused race/privacy checks passed. Exact candidate `635dec21272e64caa4c63a3e4e39b1d2aaa4d076` passed all 14 jobs in CI run `36487902997` and was fast-forwarded to main through PR #112 without changing the candidate. The redundant main-push CI was cancelled; the release workflow independently resolved the existing successful exact-candidate CI.
- Staging run `36489404361` built both images successfully, but the environment correctly rejected deployment from the feature branch. Main-branch staging run `36490863837` deployed successfully. Real Chromium and WebKit mobile login both passed, including native payload persistence, fragment cleanup, authenticated `/auth/me`, knowledge-base request and rendered page, with zero business/cleanup errors. Ancillary bootstrap data was explicitly stubbed and payments disabled; the authentication and knowledge-base chain was real. The concurrent callback test remained red because of the late-arrival boundary described above. No environment protection was relaxed, and this candidate was not promoted.
- The ten-second success-window correction passed 14 callback/cache tests under `-race -count=3` (42 executions), including fixed expiry, timer release without traffic, oldest-entry eviction, size limits, stale-timer isolation, failed exchanges, browser binding and cancellation. The late-duplicate regression was red before the correction. Handler, service and middleware suites, source checks, six upstream contracts and strict change-spec validation passed. Corrective-delta review found no implementation blocker. Fresh exact-candidate CI and real staging acceptance are still required before promotion.
- Production real-phone acceptance remains required; no claim is made that this change eliminates all login or mainland-network failures.

No payment, model, real-user account changes, database migration, paid service or new dependency is part of this correction.
